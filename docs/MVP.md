- 最初の状態確認・完了通知は、skillを呼び出したチャットで受け取れるようにする。実行ログも保存する。
- 最初の運用は、ローカル環境にリポジトリやworktreeが複数あり、それらのいずれかで開発を進める。特定のリポジトリやworktreeを想定しない。

## 初版の開発方針

以下は現時点の試作方針。利用の流れをクライアントが評価し、初版の仕様を確定する。

- Node.js 22以上と認証済みCodex CLI、Claudeを割り当てる場合は認証済みClaude Code CLIを使用する。外部ライブラリ、DB、常駐サーバーは導入しない。
- skillを呼んだチャットが進行を仲介する。CLI操作や管理用リポジトリへの移動を利用者に求めない。実行器は回答待ち・失敗・完了まで進め、質問が出たら停止する。同じチャットで受け取った回答を保存して再開する。チャットを閉じても継続する運用は、必要性を確認してから対応する。
- 自由記述は要求整理・粒度判定・設計判定を1つの計画コンテキストで順に行い、各根拠を必須にする。changeは候補列挙後、選定・実行前レビュー→タスク群ごとのapply・独立レビュー→常に最終確認を行い、completed後に同期・アーカイブする。実行前レビューの編集は対象change内だけに限定し、範囲外変更・OpenSpec検証不合格は失敗とする。plan・review・acceptanceは読み取り専用。
- 開発対象は開始時に絶対パスで指定する。ワークフローの情報は本リポジトリの`data/`に保存し、開発対象に保存しない。コードと対象のテストは開発対象に置く。
- 初版は一度に1工程を実行する。レビュー差し戻しは最大3回で、上限到達・実行エラー・中断時は人の確認を必要とする。自動コミット・公開は行わない。
- 現在の試作ではMarkdownの状態一覧を工程開始・終了時と実行中10秒ごとに更新する。チャットの稼働外では更新しない。将来のダッシュボードは、多数の並列ワークフローについてクライアントが必要な対応と優先順位を判断するための画面として、別途利用方法を評価する。
- 必要な要求、計画、回答、直近の結果だけを次工程へ渡す。チャットでの状態確認は要約を使う。工程間は別コンテキストとし、質問後は割り当てが一致すれば回答だけを渡して再開する。不一致・再開失敗・retryでは回答を含めて新規実行する。Codexの履歴は`$CODEX_HOME/sessions/`（既定`~/.codex/sessions/`）に保存する。
- `workflow.config.json`に既定の割り当てと利用枠の固定値を置く。changeはprereviewが`claude-opus-5-5`/medium、executeが`gpt-6.1-sol`/low、review・acceptanceが`gpt-6-luna`/high。requestはCLIの既存設定を使う。会話の指定を`state.models`に保存し、次の試行から優先する。CodexはWindowsのアプリ同梱版の最新、PATHの順に探索し、preflight・実行・利用枠取得で同じパスを使う。
- 工程開始前にCLIの利用枠を取得し、固定値未満ならモデルを呼ばず`limited`で停止する。実行中の上限もlimitedとし、別モデルへの変更またはリセット待ち後のretryで新規実行する。取得不能は未取得として実行する。初期値はplan・prereview・executeがセッション20%／週10%、review・acceptanceが10%／5%で、実績から見直す。各試行のCLI・モデル・推論レベル・セッション・新規／再開・前後利用枠・usageを記録する。自動切り替えと並列実行は対象外。

## 受け入れ条件

1. 指定した開発対象について全工程が進み、独立レビューを通ったタスクだけが完了扱いになる。
2. 質問中は実行を止め、回答後は同じ工程のセッションを再開でき、再開不能なら新規実行できる。
3. レビュー不合格で未完了タスクを再定義でき、無限に手戻りしない。
4. 状態、工程ごとの出力・イベント、回答、完了通知が本リポジトリに残る。
5. 同時実行、CLI失敗、不正な応答、中断を成功として扱わない。
6. 普段の開発対象のチャットから要求・回答・状態確認を行い、必要な対応と成果を受け取れる。

CLIとの接続は[非対話実行の公式仕様](https://learn.chatgpt.com/docs/non-interactive-mode)に基づく。
