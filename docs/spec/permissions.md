# 権限・昇格・承認計画

## 工程ごとの書き込み範囲

| 工程 | 書き込み |
|---|---|
| plan / review / acceptance | 不可（読み取り専用） |
| prereview | 選定したchange内。Codexは一時領域とGoキャッシュも書き込み可能 |
| execute | 開発対象、許可済みパス、一時領域、Goキャッシュ（sandbox内） |

ネットワークと作業ディレクトリ外のパスは、エージェントが`outcome=permission`で`permission.network`・`permission.paths`を要求し、`grant <ID> [--network] [--path <絶対パス>]...`で許可する。許可は案件内に保存する。

## executeの昇格の判断者

`workflow.config.json`のトップレベル`executeApprovalReviewer`で選ぶ。変更は実行器の停止中に行う。

| 値 | 判断者 |
|---|---|
| `"auto-review"`（既定） | Codexの自動レビュー |
| `"executor"` | 実行器の3層の判断（従来方式。効果の比較と切り戻し用） |

### auto-review（既定）

- sandboxに拒否された操作は、その場で昇格を要求し、Codexの自動レビューが判断する。実行器に届いた承認要求は拒否して記録する。
- 自動レビューが拒否した場合に限り、エージェントは`outcome=permission`で必要なコマンドを`permission.commands`に返して停止する。
- 所有者が`grant --command`で許可したコマンドは、確定的な許可ではなく「所有者が明示的に許可したコマンド」として入力と再開時の回答に含め、自動レビューの判断材料にする。
- この方式では全文一致の許可、スクリプトのハッシュによる束縛、`git push`を所有者へ回す判定は働かない。

### executor（3層の判断）

`;`・`&&`・改行（引用符内も含む）、ファイル変更、追加権限は許可しない。パイプは全文一致の場合だけ許可する。MCP・対話入力は取り消す。ネットワークの文脈がある要求は`grants.network`で判断する。

1. **決定的な判定**: 全文一致（空白だけ正規化）の許可があれば許可する。`git push`を含むコマンド・スクリプトは所有者へ回す。`git fetch`・`ls-remote`・`diff`・`status`・`log`・`show`・`rev-parse`の安全な形は自動で許可する（`.git`への書き込み許可がある案件を除く）。
2. **計画審査**: 承認済みで`gate=plan`の項目があれば、Codexの読み取り専用の別スレッド（`escalationReview`のモデル、担当によらず常にCodex）が項目とコマンド・スクリプトの中身を照合する。実行器は項目・リスク・審査前後の内容を検証し、固定済みの項目では実行するスクリプトの実パスとSHA-256も照合する。未固定の項目はスクリプトの内容を都度審査する。費用の確認方法が書かれていても上限を確認できない場合は所有者へ回す。許可は今回1回に限り、結果は保存しない。失敗・タイムアウト・判断不能は所有者へ回す。
3. **所有者**: 拒否して権限要求を返す。

対象内のスクリプトを実行するコマンドは`grants.commandHashes`で許可時の内容に束縛し、内容が変わると全文一致を使わない。権限要求の`permission.scripts`にスクリプトのハッシュと先頭部分を示す。接頭辞一致・セッション一括許可・恒久規則の追加は使わない。

## コマンドの許可

所有者は理由・影響と全文を確認し、要求されたコマンドだけを許可する。

```powershell
node src/cli.js grant <ID> --command "Get-CimInstance Win32_Processor"
node src/cli.js run <ID>
```

`--command`は複数指定できる。許可は`grants.commands`へ保存し、`run`で同じセッションを再開して同じコマンドを再実行させる。通常の`answer`で昇格の許可を代用しない。旧状態に`grants.commands`がなければコマンド昇格の許可なしとして扱う。ハッシュのない旧許可は有効である。

## 承認計画

外部への影響や費用を伴う操作は、実行前レビュー（自由記述ではplan）が承認計画として所有者に提示する。

- 各項目は、ID・対象タスク・操作・上限・停止条件・個別承認の要否（`gate`: `each`／`plan`）・実行スクリプト（`scripts`）・対象ファイル（`files`）・影響（`effect`: `read`／`write`／`external`）・費用上限の確認手段（`costCheck`）・追加のネットワーク・パス許可（`grants`）を持つ。
- 追加・変更分は`status`とローカルのダッシュボードに表示する。

### 承認

```powershell
node src/cli.js approve <ID> [--items <ID,...>] [条件ファイル]
```

- `--items A2,A3`ならその項目だけを承認し、省略すると承認待ちの全項目を承認する。残りがあれば回答待ちを続ける。
- 条件ファイルはUTF-8で`agent-docs/`以下に置く。条件はその呼び出しで承認した項目に付き、置き換え時に引き継がれ、再承認時に追記される。
- 承認した項目について、対象内に存在するスクリプトの実パスとSHA-256を固定する。
- `gate=plan`で申告された許可は、`grant`と同じ検証を経て案件全体に反映し、由来の項目IDを`grants.sources`に残す。項目を取り除いた後も許可は有効。検証に失敗した場合は承認待ちを保つ。

### 承認と差し戻しの混在・変更

- 承認する項目を先に`approve --items`で登録し、残りの修正や拒否を`answer`で伝える。承認待ちの項目は差し戻し済みとして保持し、採番を引き継いで実行前レビューへ戻る。
- 継続できるのは承認済みの項目で、差し戻し済みの項目は変更元に使える。差し戻し済みの項目の変更は承認待ちにし、再提案されなかった項目はレビュー成功時に取り除いて記録する。
- 不要になった承認済みの項目は取り除いて記録する。所有者の回答だけに基づく承認済み項目の変更は、計画審査が回答の範囲内と判定すれば、固定情報を引き継いで置き換える。
- 承認範囲に合わせてchangeを分割・書き換えない。範囲が足りなければ`outcome=approval`で残り全体の計画を出し直す。

## 記録

- 短い`status`は回答待ちの要求コマンドを示す。
- `status <ID> --detail`は許可コマンド・全昇格履歴（判断の層`layer`・審査`review`・担当`cli`）・層ごとの件数`escalationCounts`・承認項目のID`approvalItems`・`execpolicyRules`を返す。
- 要求と判断は`events.jsonl`の`escalation_requested`・`escalation_decided`、試行の`invocation.json`、`state.evidence[].escalations`に残り、理由・作業ディレクトリ・判断時刻・一致した許可を追跡できる。
- 自動レビューの完了通知は`layer: "autoReview"`として記録する。通知がなければ`escalationCounts.autoReview`は`null`（未取得）とし、0件と区別する。
