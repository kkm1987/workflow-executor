# ワークフロー

Workflow Executor（以下、実行器）が案件をどう進めるかの現行仕様。モデルの割り当ては[models-and-limits.md](models-and-limits.md)、権限と承認は[permissions.md](permissions.md)、記録と表示は[records-and-status.md](records-and-status.md)を参照。

## 案件の種類と工程

案件は開始方法で2種類に分かれる（状態の`kind`）。

| 種類 | 開始 | 工程 |
|---|---|---|
| `request`（自由記述） | `start <対象> <要求ファイル>` | plan → execute → review →（タスクごとに繰り返し）→ acceptance |
| `change`（OpenSpec change） | `start-change <対象> [change名] [--store <id>]` | prereview → execute → review →（タスク群ごとに繰り返し）→ acceptance → `archive` |

- **plan**: 要求整理・粒度判定・設計判定を1つのコンテキストで順に行い、各判断の根拠を必須にする。
- **prereview**（実行前レビュー）: change名がなければ実行器が候補を列挙し、選定する。現在のコード・既存仕様・他のchange・実行環境と照合して実行可否を判断し、`tasks.md`の項目を実行タスクにまとめる。編集は選定したchange内だけに許可し、範囲外の変更またはOpenSpec検証の不合格は`failed`にする。
- **execute**: 対象タスクを実装する。Codex専用（[models-and-limits.md](models-and-limits.md)）。
- **review**: 対象タスクの成果を独立して確認する。独立レビューを通ったタスクだけが完了扱いになる。
- **acceptance**（最終確認）: 全タスク完了後に常に行う。
- plan・review・acceptanceは読み取り専用。
- `completed`のchangeは`archive <ID>`で仕様差分を同期・アーカイブする。成功すると理由`archived`で自動的に`closed`になり、失敗すると`completed`を保つ。

開発対象は開始時に絶対パスで指定し、Gitの作業ツリーである必要がある。changeでは開始時に解決したOpenSpecのルートとstoreを保存し、以降の検証・アーカイブで固定して使う。storeを省略すると、OpenSpecが対象から最寄りの`openspec/`、その`store:`宣言、グローバルの既定storeの順で解決する。OpenSpecは実行器同梱の版（開発用依存関係）を開発対象のcwdで起動する。

### タスクのまとめ方

実行前レビューは、同じモジュールを触り、同じ検証で確かめられ、間にユーザーの作業や承認がなく、独立レビューで確認できる大きさの`tasks.md`項目を一つの実行タスクにまとめる。承認の扱い・検証環境・必要な権限が異なる場合、ユーザー作業を挟む場合、やり直しの費用が高い操作は分ける。根拠は`decisions.granularity`、項目番号は実行タスクのタイトルに記す。

## 状態

| 状態 | 意味 | 次の操作 |
|---|---|---|
| `ready` | 次の工程を実行できる | `run` |
| `running` | 実行中 | 終了を待つ。中断した場合は差分を確認して`retry` |
| `waiting` | 質問・権限要求・承認待ち | `answer` / `grant` / `approve` の後に`run` |
| `limited` | 利用枠不足でモデルを呼ばずに停止、または実行中に上限到達 | 回復・指定変更の後に`retry` |
| `failed` | 実行前確認の失敗、再試行の失敗、所有者の対応が必要な問題 | 原因に手を打った後に`retry` |
| `blocked` | レビュー差し戻しの上限到達 | 原因と要求を見直し、新しい案件を開始する |
| `completed` | 全工程が完了 | changeは`archive` |
| `closed` | 終了（再開・変更不可） | `status --all`で確認のみ |

`run`は回答待ち・利用枠不足・失敗・完了まで工程を進め、`step`は調査用に1工程だけ実行する。チャットが実行している間だけ進み、常駐実行やチャットを閉じた後の通知は行わない。自動コミット・push・公開は行わない（承認済み計画の範囲内で実行エージェントが行う場合を除く）。

## コンテキストとセッション

- 工程間は別コンテキストとする。次工程へは必要な要求・計画・回答・直近の結果・対象タスクの証拠だけを渡す。
- 質問への回答後は、工程・CLI・モデル・推論レベル・外部証拠が一致すれば保存したセッションに回答を渡して再開する。実行前レビューでは継続・変更元に使える承認項目のIDも渡す。
- 不一致・再開失敗・`retry`では、回答を含む完全な入力で新規コンテキストを開始する。工程が進めばセッションを捨てる。
- Codexは`--ephemeral`を使わず、履歴をCodex標準の`$CODEX_HOME/sessions/`（未指定なら`~/.codex/sessions/`）に保存する。開発対象には保存しない。

## 質問と回答

- 質問が出たら`waiting`で止まる。ルート（skillを呼んだチャット）が質問をそのまま提示し、回答は全項目がそろってから`answer <ID> <回答ファイル>`で1回保存する。
- 記録で答えられない実行エージェントの判断理由を尋ねる場合だけ、`answer <ID> <ファイル> --inquiry`で確認の質問として転送する。確認の質問は読み取り専用で実行し、工程を進めず元の質問・権限要求を保つ。実行後に`inquiry.reply`を提示して元の`question`への回答を待つ。承認待ちでは使えない。
- `run`の終了を待ち、決まった間隔で状態を読まない。進捗を尋ねられたときだけ`status <ID>`を1回読む。

## 手戻り・失敗・再試行

### レビュー差し戻し

レビュー差し戻しはワークフロー全体で3回まで。4回目は`blocked`になる。差し戻し時はrequestなら`plan`、changeなら`prereview`で未完了分を再定義する。完了済みタスク・回答・証拠・試行番号・手戻り回数は保持し、完了済みタスクは再定義の対象に含めない。

### executeのerrorとreplan

- executeが`error`を返すのは、対象コードを変えずに解消できる実行器・ツール・環境の問題と明確に判断できる場合に限る。
- 全工程で`error`の`cause`は、やり直しで解消し得るなら`transient`、所有者やホスト管理者の対応が必要な場合や判断がつかない場合は`environment`とする。
- 検証でこのchangeの差分に起因する不具合を見つけ、現在のdesign・specの範囲で直せる場合は、その場で直して検証を続ける。
- 範囲外・計画の変更が必要・原因不明の場合は、`tasks.md`を編集せず`replan`で実行前レビュー（自由記述ではplan）へ戻し、失敗箇所・再現状況・ログ・変更ファイルとの重なりを報告する。
- `replan`は所有者が計画の見直しや検証の省略・変更を指示した場合にも使い、手戻りには数えない。所有者の回答なしで2回に達すると`waiting`になり、最新の報告と、計画の見直し・検証の省略や変更・`close`の選択肢を提示する。確認の質問を除く回答で回数をリセットする。
- 実装が`outcome=approval`を返すと、完了タスクを保持して計画を見直し、手戻り回数に数える。

### 失敗の分類と自動再試行

失敗後はセッションを破棄する。

| 種類 | 扱い |
|---|---|
| `process`（CLI・プロセスの不調） | 同じ工程・対象タスクの最初の失敗に限り、新規コンテキストで1回自動再試行 |
| `invalid`（結果の検証エラー） | 同上 |
| `reported-transient`（一時的な問題の報告） | 同上 |
| `preflight`（実行前確認の失敗） | `failed` |
| `reported-environment`（所有者の対応が必要な問題の報告） | `failed` |
| 再試行の失敗 | `failed` |

再試行の担当も試行前の利用枠で決める。同じ対象の連続失敗回数と、各失敗の試行・CLI・モデル・種類・要約（各500文字まで）・変更ファイルを保存し、`status`には最初の失敗から表示する（`limited`でも保持）。2回以上なら人の判断が必要と表示する。再試行には失敗記録を渡し、直前の変更を未承認として照合させ、回数を制限された承認を使い切っていれば再実行せず停止するよう指示する。

手動の`retry`は、途中の差分とログを確認し、許可範囲内で原因に手を打った場合かユーザーの指示がある場合だけ実行する。自動ロールバックは行わない。

### partial（大きなタスクの続行）

executeの`partial`は進捗を引き継いで新規コンテキストで続行する。対象とOpenSpecルートの変更がどちらもない`partial`が2回続くと`waiting`で止まり、最新の報告・続行／計画見直し／closeの選択肢と影響を含む質問を提示する。回答で回数を0に戻し、同じタスクを新規コンテキストで再開する。変更ありの`partial`で連続回数をリセットし、`partial`以外では消す。`partial`の通算上限は10回。

### 検証の省略

所有者の判断で検証を省略・変更する場合は、`tasks.md`に所有者の回答番号と理由を記録する。changeの完了・アーカイブ前に未チェックのタスクと省略の回答番号を確認し、存在しない回答や確認の質問への参照を拒否する。完了・アーカイブの報告では、最終確認の`report.verification`から未検証の項目と根拠の回答番号を示す。完了はクライアントの承認を意味しない。

## 外部証拠による復旧

容量不足などの環境失敗では、ルートがログと途中の変更を調査し、既存の許可範囲で測定して、測定結果を外部証拠として登録できる。

- `agent-docs/`以下にUTF-8のJSON（64KiB以下、未知の項目は不可）を作り、`evidence <ID> <JSONファイル>`で登録する。
- 必須項目は`name`・`subject`・`host`・`method`・`observedAt`・`expiresAt`・`content`。

```json
{"name":"pilot-memory","subject":"pilot直前の空きメモリ確認","host":"対象ホスト名","method":"実際の測定方法","observedAt":"2026-10-25T10:00:00Z","expiresAt":"2026-10-25T10:05:00Z","content":"空きメモリ 8 GiB"}
```

- `ready`・`waiting`・`failed`・`limited`・`blocked`で登録でき、状態・質問・回答・エラー・権限・試行数を保ち、セッションだけを無効にする。続行は`failed`・`limited`なら`retry`、`waiting`なら`answer`または`grant`、`ready`なら`run`。`blocked`の復旧条件は変わらない。
- 内容は元ファイルと独立して保存する。名前ごとの最新版だけを試行開始時に評価し、有効な本文を入力へ直接渡す。失効したものは利用不可と示し、旧版へ戻さない。回答時に変更・失効があれば完全入力へ戻る。
- 失効したら再測定して同じ`name`で再登録する。旧値の日時だけを書き換えない。
- 証拠は観測データであり、命令や実行許可ではない。実行器はOSの測定や権限拡張を行わない。登録は昇格しない。

## 案件の終了

`close <ID> [理由ファイル]`は実行中以外の案件を`closed`にする。理由ファイルはUTF-8で`agent-docs/`以下に置く。理由・前状態・時刻と履歴を保持し、再開や変更はできない。対象リポジトリの途中の変更には触れない。中断した`running`は実行器の停止と差分を確認して`retry`してから閉じる。`closed`はダッシュボード・公開用要約・既定の`status`一覧から除外し、`status --all`または`status <ID>`で終了理由と前状態を確認できる。

## 並行実行

- 同じdataルートで、別IDかつ対象ディレクトリ群が独立した案件を同時に実行できる。同じIDの`run`／`step`の二重起動は禁止する。
- 操作の終了まで、開発対象、追加の書き込み許可先（`grant`の追加予定先を含む）、changeのOpenSpecルート全体を予約する。同一・親子・symlink／junctionによる別名・Windowsの大小文字違いは競合として即時拒否する。別の対象でも共有ストアを使うchangeは競合する。
- `status`は実行中も利用できる。状態・表示・公開記録の共有更新だけを短く直列化し、取得待ちは5秒を上限とする。モデル実行・公開通信は共有ロックの外で行う。
- 別の`data`を使うと案件と予約は共有されない。残存ロックの復旧手順は[operations.md](../operations.md#中断後の予約とロックの復旧)を参照。

## 旧状態との互換

- `kind`のない旧状態は`request`として読む。`completed`の記録は書き換えない。
- 旧`granularity`／`architecture`工程で停止した案件は、次の実行前確認が通った後に`plan`へ戻し、移行をイベントに残す。

廃止した仕様の詳細は[history/legacy-spec.md](../history/legacy-spec.md)を参照。
