## Context

実行器はNode.js標準機能で状態を保存し、各工程を新しい`codex exec --ephemeral`で実行する。クライアントは普段の開発対象のチャットからskillを呼び、回答と完了報告を受け取る。

今回の測定は1タスク・6種類の工程・7試行。独立した成果確認8項目と生成テスト11件は成功した。

| 測定項目 | 結果 |
| --- | ---: |
| 工程の稼働時間合計 | 355.6秒 |
| 停止・調査を含む経過時間 | 744.0秒 |
| 入力トークン | 742,580 |
| 入力のうちキャッシュ | 560,768 |
| 出力トークン | 8,396 |
| 停止した実装試行の入力 | 148,745 |
| 要求整理・粒度確認・設計確認の合計 | 124.3秒、入力279,658 |

キャッシュ入力は入力の内訳で、別途加算しない。元データは今回のローカル評価記録であり、クローン先でも検証できるよう評価用の要求と独立した検証をテスト資産として残す。

## Goals / Non-Goals

目標は、実行不能な環境へのモデル呼び出しを防ぎ、3つの計画判断の品質を保ちながらコンテキスト起動を減らすこと。また、性能とクライアントの必要な対応を確認できるようにする。

常駐・並列運用、別の実行バックエンド、モデル最適化、ブラウザ用ダッシュボード、業務上の優先度スコア、成果確認済みの追跡は対象外。ダッシュボードは当面Markdownのまま改善する。

## Decisions

### 1. 実行前確認を1回行う

`run`がreadyのワークフローを進める前に、対象の存在、Git作業ツリー、CLIの起動・認証、必要なサンドボックスでのコマンド起動を確認する。実装が必要なら書き込み用プロファイルの起動も確認する。`step`から直接実行する場合にも確認を省略しない。

検査はモデルを使わず、対象のコードを実行・変更しない。タイムアウトを設け、結果を`data/<ID>/`に保存する。同じ`run`内で工程ごとに繰り返さず、別の再開操作では再確認する。認証情報は記録せず、サンドボックス起動確認を全操作・全パスの書き込み保証として扱わない。

WindowsのMXC優先設定は既存実装を利用する。検査失敗時はfailedとして原因と復旧の担当を示し、自動的な権限拡大やサンドボックス無効化は行わない。

### 2. 計画を1コンテキストにまとめる

新規ワークフローは`plan → execute → review → acceptance`とする。plan内で要求整理、粒度判定、設計判定を順に行い、各判断の根拠と未完了タスクの完全な一覧を返す。実行器は3つの判断結果がそろっているか確認する。

不明な業務判断があればwaitingで止まり、回答を保存してplanを新しいコンテキストで再実行する。レビュー差し戻しもplanへ戻し、完了済みタスクとその成果を保持して未完了分だけ再定義する。実装とレビューに会話履歴を共有せず、必要な要求・タスク・判断結果・証拠だけを渡す。

旧granularity/architectureで停止中の状態は、再開時にplanへ戻すことを記録する。完了済みタスク・回答・証拠・試行番号・手戻り回数を維持する。completedの履歴は移行しない。

3つの確認を独立コンテキストのまま維持する案は、品質比較の対照として使う。resumeによる計画セッションの継続は、セッションの永続化・復旧が増えるため採用しない。

### 3. 技術的失敗をクライアントの質問と分ける

`outcome=error`とMXC優先設定は実装済み。今後は実行前確認の失敗も同じfailedへ統合する。failed/blockedはまず開発主体が調査する状態として示し、追加の権限・要求の判断が本当に必要な場合だけ、理由と具体的な質問をクライアントへ提示する。

### 4. 通常のログから性能を評価する

工程の開始・終了イベントとCodexのusageを使い、試行番号、工程、成否、時間、入力・キャッシュ入力・出力を記録する。usage欠落は未取得として扱う。失敗・再試行も含め、工程稼働と待ち時間を含む経過時間を分ける。このチャットのトークンや金額は推定しない。

計測・レポート生成にモデルを使わず、測定済みの値をそのまま集計する。短い要約をチャットに返し、詳細は本リポジトリ内のファイルへリンクする。

### 5. ダッシュボードは必要な対応を先に見せる

案件名は要求の見出し等から短く付け、フルID・フルパスは詳細へ移す。状態と工程を日本語にし、回答待ち、開発主体の復旧・再計画待ち、成果確認可能、進行中の順でグループ化する。これは対応の種類による表示順で、締切や事業上の重要度を推測した順位ではない。

回答待ちには質問と停止理由を、復旧待ちには原因と担当を、完了には成果・検証結果へのリンクを示す。表示用の文字列はMarkdownの表を壊さないよう処理する。試作をクライアントに紹介してから、追加の操作や表示方法を判断する。

## Risks / Trade-offs

- 計画をまとめることで判断の省略が起きる可能性があるため、3つの判断結果の必須化と独立レビューで確認する。
- モデルや通信の揺らぎがあるため、過去の失敗込み測定から改善率を算出しない。同じ要求・モデル・推論設定・実行環境で対照と改善版を各3回測定し、中央値と各回の値を残す。キャッシュの条件差も明記する。
- 正常・無質問・無差し戻しの1タスクでは、モデルコンテキストの起動を6回から4回へ減らす。時間・入力・非キャッシュ入力・出力の改善は実測で判定し、悪化した指標は隠さない。数値のSLAや削減率はクライアント合意前に設定しない。
- 実行前確認の後に障害が起きることはあるため、途中変更の記録と復旧手順は維持する。

## Migration Plan

既存のエラー分類を維持したまま、実行前確認、計測、計画の統合、表示改善の順に実装する。保存済み状態の再開テストを行い、skill・CLI・利用文書の工程説明を合わせる。問題があれば計画の統合を戻し、旧工程を再実行できるよう、履歴を破壊しない。
