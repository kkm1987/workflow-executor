## MODIFIED Requirements

### Requirement: 実行前に環境を確認する
実行器は、run/stepでモデルを呼ぶ前に、開発対象・Git作業ツリー・ワークフローが使う各CLIの起動と認証・必要なサンドボックスでのコマンド起動をモデルなしで確認しなければならない（MUST）。確認には有限のタイムアウトを設け、対象のコードを実行・変更せず、使用するCLIの実行ファイルと版を含む結果を本リポジトリに保存する。

#### Scenario: 実行不能な環境で開始する
- **WHEN** 実行前確認が失敗またはタイムアウトする
- **THEN** モデル呼び出しは0回で、状態はfailedになり、失敗原因と復旧に必要な情報が保存される

#### Scenario: 正常な環境で連続実行する
- **WHEN** 実行前確認に成功したrunが複数工程を進める
- **THEN** 同じrun内で確認を重複せず、別の再開操作では確認し直す

#### Scenario: Claudeを使う工程がある
- **WHEN** ワークフローのいずれかの工程にClaudeが割り当てられている
- **THEN** CodexとあわせてClaude CLIの起動と認証も確認する

### Requirement: 計画の3つの判断を共有コンテキストで行う
実行器は、要求整理・粒度判定・設計判定を1つの計画コンテキストで実施し、各判断の根拠と順序付きの未完了タスクを記録しなければならない（MUST）。いずれかの判断が欠けた応答を計画完了として扱ってはならない。

#### Scenario: 小さな要求を計画する
- **WHEN** 要求が確定した小さな1タスクを計画する
- **THEN** 1つの計画コンテキストで3つの判断を記録し、適切な受け入れ条件を持つタスクを返す

#### Scenario: 業務判断が不足している
- **WHEN** 計画にクライアントの判断が必要な不明点がある
- **THEN** waitingで停止して同じチャットに質問し、回答を保存した後で計画のセッションを再開する

### Requirement: 実装と独立レビューを分離する
実行器は、各タスクの実装とレビュー、および最後の要求充足確認をそれぞれ別のコンテキストで実行しなければならない（MUST）。ある工程のセッションを別の工程に引き継いではならない。無質問・無差し戻しの1タスクは計画・実装・レビュー・最終確認の4コンテキストで完了する。

#### Scenario: 正常な1タスクを完了する
- **WHEN** 1タスクが追加の質問や差し戻しなしで全工程を通過する
- **THEN** コンテキストは4個すべて異なり、独立レビューと最終確認の合格後にcompletedとなる

#### Scenario: レビューで差し戻す
- **WHEN** レビューが修正を要求する
- **THEN** 未完了分をplanで再定義し、完了済みタスクの成果・証拠と既存の手戻り上限を保持する

## ADDED Requirements

### Requirement: 工程ごとに実行CLI・モデル・推論レベルを指定する
実行器は、工程ごとに実行CLI（CodexまたはClaude）・モデル・推論レベルを決め、その値で工程を実行しなければならない（MUST）。既定値は本リポジトリの設定で変更でき、ルートセッションの会話でクライアントが指定した値をワークフローごとに保存して既定値より優先する。途中で変更した値は次に開始する試行から使う。未知のCLIや、そのCLIで指定できない推論レベルは実行前に拒否する。

#### Scenario: 既定値で実行する
- **WHEN** クライアントが何も指定せずにchangeのワークフローを進める
- **THEN** 実行前レビューは`claude-opus-5-5`/medium、applyは`gpt-6.1-sol`/low、独立レビューと最終確認は`gpt-6-luna`/highで実行される

#### Scenario: 会話で工程のモデルを変更する
- **WHEN** クライアントが独立レビューのモデルを変更するよう指示する
- **THEN** ワークフローに変更が保存され、以後の独立レビューの試行だけが新しいモデルで実行される

#### Scenario: 不正な指定
- **WHEN** 指定されたCLIが未対応、または推論レベルがそのCLIで使えない
- **THEN** 保存せずに拒否し、モデルを呼ばない

### Requirement: 利用枠を事前に確認する
実行器は、各工程の開始前に、その工程のCLIの利用枠の残りを取得し、工程ごとに設定した固定値と比べなければならない（MUST）。残りが固定値を下回る場合はモデルを呼ばずに停止し、別のモデルの使用をクライアントに提案できる状態にする。実行中に利用枠の上限へ達した場合は、他の技術的失敗と区別して記録する。モデルを自動で切り替えてはならない。利用枠を取得できない場合は、その旨を記録して工程を実行する。

#### Scenario: 利用枠が不足している
- **WHEN** applyの開始前に、Codexの利用枠の残りがapplyの固定値を下回る
- **THEN** モデル呼び出しは0回で停止し、利用枠の状況と、別モデルへの変更が必要なことを示す

#### Scenario: 提案を受け入れて再開する
- **WHEN** クライアントが提案された別のモデルを受け入れる
- **THEN** その工程のモデルを変更して保存し、新規コンテキストで工程を実行する

#### Scenario: 実行中に上限へ達する
- **WHEN** 工程の実行中にCLIが利用枠の上限で終了する
- **THEN** 利用枠の上限による失敗として記録し、別モデルの提案ができる状態にする

#### Scenario: 利用枠を取得できない
- **WHEN** CLIの利用枠の表示形式が想定と異なり、残りを読み取れない
- **THEN** 取得できなかったことを記録し、事前の判定をせずに工程を実行する

### Requirement: 質問への回答後に同じセッションを再開する
実行器は、ある工程が質問で停止して回答を受け取った場合、その工程の同じセッションを再開して回答を渡さなければならない（MUST）。工程のCLIやモデルが変わった場合、再開に失敗した場合、失敗・中断からretryする場合は、回答を含む必要な情報を渡して新規コンテキストで実行する。再開したセッションを他の工程に使ってはならない。

#### Scenario: 実装中の質問に回答する
- **WHEN** applyが質問で停止し、クライアントの回答を保存して再開する
- **THEN** applyの同じセッションに回答を渡して作業を続ける

#### Scenario: 回答時にモデルを変更する
- **WHEN** 質問への回答とあわせて、その工程のモデルが変更される
- **THEN** 新しいモデルの新規コンテキストで、回答を含めて工程を再実行する

#### Scenario: セッションを再開できない
- **WHEN** 保存したセッションの再開がエラーになる
- **THEN** 失敗を記録し、新規コンテキストで同じ工程を実行する

### Requirement: Codexの実行ファイルを探索する
実行器は、Codexの実行ファイルを、デスクトップアプリに同梱された最新版、`PATH`上の`codex`の順に探さなければならない（MUST）。見つからない場合は実行前確認で失敗とする。

#### Scenario: デスクトップアプリだけがある
- **WHEN** `PATH`に`codex`がなく、デスクトップアプリの同梱版がある
- **THEN** 同梱版の最新のものを使い、そのパスと版を実行前確認に記録する

#### Scenario: どちらもない
- **WHEN** 同梱版も`PATH`上の`codex`も見つからない
- **THEN** モデルを呼ばずにfailedとし、Codexの導入が必要なことを示す
