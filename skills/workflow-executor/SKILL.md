# Workflow Executor

実行器のルートはこのskillフォルダーの2階層上。リンクから読んだ場合はリンク先の実体パスを使う。以下のCLIパスを絶対パスへ解決し、実行器ルートを作業ディレクトリとして実行する。Node.js 22以上と認証済みCodex、Claudeを割り当てる場合は認証済みClaude Code CLIが必要。

状態確認・既存ワークフローへの回答・再開の場合は、新規開始の手順に入る前に保存済み状態を読む。チャットに記録されたIDを使い、不明なら`node src/cli.js status`で一覧を取得し、開いている開発対象と照合する。候補が複数なら対象を確認する。状態確認だけの依頼では状態と必要な対応を報告して終了する。既存の質問への回答なら手順4、続行依頼なら手順2〜3へ進む。

1. 開発対象はユーザーが開いているリポジトリ・worktreeを使う。明示された対象があればそちらを優先し、判別できない場合だけ確認する。changeの実行依頼なら`node src/cli.js start-change <対象の絶対パス> [change名]`で開始する。名前がなければ実行器が候補を列挙し、実行前レビューが選定する。自由記述の要求は不足をチャットで確認し、`agent-docs/`以下にUTF-8で保存して`node src/cli.js start <対象の絶対パス> <要求ファイル>`を実行する。IDを記録する。CLI操作や管理用リポジトリへの移動をユーザーに求めない。
2. 会話で指定されたモデル・推論レベルは`model <ID> <工程> <モデル> [推論レベル]`で保存する。開始時には`start-change`へ`--model <工程> <モデル> [推論レベル]`を繰り返して渡せる。指定がなければ`workflow.config.json`の既定値を使う。実行前に各工程のCLI・モデル・推論レベルを復唱する。ルートのモデルはクライアント設定に任せ、質問・回答の仲介に徹する。
3. `node src/cli.js run <ID>`で回答待ち・利用枠不足・失敗・完了まで進める。changeは選定・実行前レビュー→タスク群ごとのapply・独立レビュー→常に最終確認、自由記述は計画→実装・独立レビュー→最終確認。工程間は別コンテキスト、質問への回答後は同じ工程のセッションを再開する。ツールが実行中なら終了まで待ち、並行してrunやstepを呼ばない。進捗はこのチャットで伝え、状態確認は`status <ID>`の短い要約を使う。詳しい調査時だけ状態ファイルとログを読む。ダッシュボードはユーザーが見たい場合に開く。
4. `waiting`なら`question`をそのままこのチャットに提示して止まる。回答も解釈・補足せず`agent-docs/`の回答ファイルへ保存し、`node src/cli.js answer <ID> <回答ファイル>`を実行して手順3へ戻る。要求や業務判断の回答を勝手に補わない。
5. `limited`なら取得した利用枠・リセット時刻を示し、別モデルへの変更またはリセット待ちを提案して止まる。同じCLIのモデルが利用枠を共有する場合も考慮する。自動切り替えはしない。ユーザーの指定後は`model`で変更し、復唱して手順3へ戻る。リセット待ち後は`retry <ID>`で新規コンテキストにする。
6. `completed`のchangeは`node src/cli.js archive <ID>`で仕様差分を同期・アーカイブし、結果を報告する。失敗したらcompletedを保ってエラーを提示し停止する。自由記述のcompletedは成果・検証結果へのリンクと変更先を報告する。`failed`ならエラーを読み、実行前確認の失敗は`preflight-*.json`、工程実行後の失敗は該当attemptのログを調べる。途中の変更を確認し、原因を修正できた場合は`retry <ID>`で再開する。変更の扱いが不明な場合は確認する。`blocked`は手戻り上限なので、原因と必要な判断を提示して止まる。ユーザー自身の対応が必要かを伝える。

再開時は`node src/cli.js status <ID>`で保存済み状態を読む。実行器のデータを開発対象へ書かない。対象へのコミット、push、公開は別の明示的な依頼がある場合だけ行う。中断したロックの復旧は[README](../../README.md)を読む。

チャットが実行している間だけ進む。常駐実行やチャットを閉じた後の通知を約束しない。状態は10秒ごとと工程境界でMarkdownダッシュボードに保存される。
