# Workflow Executor

実行器のルートはこのskillフォルダーの2階層上。リンクから読んだ場合はリンク先の実体パスを使う。以下のCLIパスを絶対パスへ解決し、実行器ルートを作業ディレクトリとして実行する。Node.js 22以上と認証済みCodex、Claudeを割り当てる場合は認証済みClaude Code CLIが必要。

状態確認・既存ワークフローへの回答・再開の場合は、新規開始の手順に入る前に保存済み状態を読む。チャットに記録されたIDを使い、不明なら`node src/cli.js status`で一覧を取得し、開いている開発対象と照合する。候補が複数なら対象を確認する。状態確認だけの依頼では状態と必要な対応を報告して終了する。既存の質問への回答なら手順4、続行依頼なら手順2〜3へ進む。

1. 開発対象はユーザーが開いているリポジトリ・worktreeを使う。明示された対象があればそちらを優先し、判別できない場合だけ確認する。引数なしでskillを呼び出した場合は、OpenSpecの次に実行すべきchangeの選定から開始する。要求やchange名の入力を求めず、`node src/cli.js start-change <対象の絶対パス>`を実行する。changeの実行依頼も`node src/cli.js start-change <対象の絶対パス> [change名]`で開始する。名前がなければ実行器が候補を列挙し、実行前レビューが選定する。storeが指定された場合は`--store <id>`を付ける。省略時はOpenSpec自身が対象から最寄りの`openspec/`、その`store:`宣言、グローバルの既定storeの順で解決する。開始時に保存したルート・storeを以降も使い、ルートのGit作業ツリーを実行前に確認する。自由記述の要求は不足をチャットで確認し、`agent-docs/`以下にUTF-8で保存して`node src/cli.js start <対象の絶対パス> <要求ファイル>`を実行する。IDを記録する。CLI操作や管理用リポジトリへの移動をユーザーに求めない。
2. 通常モデル・推論レベルは`model <ID> <工程> <モデル> [推論レベル]`で保存する。start・start-changeは`--model <工程> <モデル> [推論レベル]`と`--fallback <工程> <モデル> [推論レベル]`を繰り返せる。代替は1工程1候補の別CLIに限り、同じCLIになる通常側の変更も拒否する。未指定なら`workflow.config.json`の`models.request/change`と任意の`fallbacks.request/change.<工程>`（値は`{ "model": "...", "effort": "..." }`）を使う。既定の代替はない。案件指定を優先し、停止中は`fallback <ID> <工程> <モデル> [推論レベル]`で変更、`fallback <ID> <工程> --disable`で案件にnullを保存して既定の代替も無効化する。設定だけで再開せず、状態・質問を保持する。例: `node src/cli.js start-change <対象> <change名> --fallback execute claude-opus-5-5 medium`。実行前に各工程の通常・代替のCLI・モデル・推論レベルを復唱する。ルートのモデルはクライアント設定に任せ、質問・回答の仲介に徹する。
3. `node src/cli.js run <ID>`で回答待ち・利用枠不足・失敗・完了まで進める。changeは選定・実行前レビュー→タスク群ごとのapply・独立レビュー→常に最終確認、自由記述は計画→実装・独立レビュー→最終確認。工程間は別コンテキスト、質問への回答後は同じ工程のセッションを再開する。同じIDのrun／step二重起動は禁止し、実行中なら終了まで待つ。同じdataルートの別IDで、対象・追加許可先・OpenSpecルート全体が独立した案件だけ並行操作できる。同一・親子・symlink／junctionの別名・Windows大小文字違いは競合し、別対象でも共有ストアは競合する。grantの追加先も更新前に判定する。runは、バックグラウンド実行と終了通知を使えるクライアントではそれを利用し、使えなければフォアグラウンドで終了を待つ。決まった間隔でstatusを読まない。終了後は出力の最後の行（短い要約）を読み、次の手順へ進む。ユーザーが進捗を尋ねたときだけ`status <ID>`を1回読んで答える。詳しい調査時だけ`status <ID> --detail`・状態ファイル・ログを読む。ダッシュボードはユーザーが見たい場合に開く。
3a. 大きなchangeの実装が`partial`なら進捗を引き継いで新規コンテキストで続行する。対象とOpenSpecルートの変更がどちらもないpartialが2回続くと`waiting`になるので、質問をそのまま提示して止まる。回答で回数をリセットし、同じタスクを続ける。変更のあるpartialは`run`が自動続行し、`ready`で戻った場合は同じ`run <ID>`を再実行する。partialの通算上限10回は変わらない。
3b. `waiting`で`status`に`permission`（ネットワーク・ワーキングディレクトリ外パスの要求）があれば、次の範囲に限りルートが自分で許可する: ネットワークは依存関係の取得や公式ドキュメントの参照など、タスクに必要な読み取り・取得目的。パスは要求・changeの成果物・対象リポジトリの関連worktreeなど、タスクに必要な最小限のディレクトリ。保存済みの`approval.status`が`approved`で、計画と所有者の条件の範囲内の操作に必要なネットワーク・パスもルートが許可してよい。`node src/cli.js grant <ID> [--network] [--path <絶対パス>]...`を実行して手順3へ戻る。アクセス権の理由でgrantが失敗した場合は許可を繰り返さず、対象パスとOSのアクセス権の修正が必要であることをユーザーへ提示する。次は許可せず、要求内容をユーザーへ提示して判断を仰ぐ: 認証情報・鍵・システム設定に関わるもの、ホーム直下やドライブ全体などの広い範囲、承認されていない取得物の実行・公開・送信・push。
3c. `waiting`で`status`の`approval.status`が`pending`なら、承認計画の全項目を対象タスク・操作・上限・停止条件の一覧にして一度に提示し、所有者の判断を待つ。所有者が計画全体を承認（条件付きを含む）したら、条件を解釈・補足せず`agent-docs/`のUTF-8ファイルへ保存し、`node src/cli.js approve <ID> [条件ファイル]`で登録して手順3へ戻る。条件なしならファイルを省略する。範囲の修正や拒否は`answer`で伝えて実行前レビューへ戻す。承認範囲に合わせてchangeを分割・書き換えない。範囲が足りなければ`outcome=approval`で残り全体の計画を出し直す。
4. 上記以外の`waiting`なら`question`をそのままこのチャットに提示して待つ。待機中のユーザーの発言は、回答と確認の質問に分ける。区別できなければ回答として扱ってよいかユーザーに確認する。確認の質問には`status <ID> --detail`・状態ファイル・試行の`result.json`と元ログ・changeのproposal／design／tasks／仕様の差分を読み、根拠ファイルのパスを示して答え、`answer`しない。回答は全項目がそろうまでチャット内で保持し、不足項目だけを尋ねる。そろったら解釈・補足せずユーザーの言葉のまま`agent-docs/`のUTF-8回答ファイルへまとめ、`node src/cli.js answer <ID> <回答ファイル>`を1回だけ実行して手順3へ戻る。記録に根拠がなく実行エージェントの判断理由が必要な場合だけ、確認の質問を同フォルダーのファイルへ保存して`node src/cli.js answer <ID> <ファイル> --inquiry`で転送し、手順3のrunで説明を受け取り提示して元の質問への回答を待つ。承認待ちには--inquiryを使わない。要求や業務判断の回答を勝手に補わない。
5. 各試行は通常側から枠を確認し、閾値未満なら指定済みの代替を評価する。通常側の失敗で切り替えた工程・タスクでは、残枠によらず代替を使い続け、工程・タスクが変われば通常側に戻る。代替は取得できた窓が1つ以上あり、すべてが工程の閾値以上なら実行する。通常側の全窓取得不能は通常側で実行する。代替未指定・不足・全窓取得不能はモデル0回で`limited`となる。候補別の枠・リセット時刻・選択理由を示し、指定変更か回復待ちを提案して止まる。例えば`node src/cli.js fallback <ID> execute claude-opus-5-5 medium`、無効化は`node src/cli.js fallback <ID> execute --disable`。指定変更・回復後は`node src/cli.js retry <ID>`から手順3へ戻る。通常側は`model`で変更できる。枠はCLI単位であり、モデル固有の残枠を保証しない。実行途中の上限到達は途中の記録を保持して停止し、自動切替・自動再試行しない。選択した代替の確認失敗はfailedとして手順6へ進み、権限を追加したと解釈しない。通常設定は保持する。担当変更時は回答・承認・証拠を含む完全入力を渡し、同担当なら既存の再開条件に従う。実担当と選択理由はstatus・ダッシュボード・試行記録で確認する。
6. `completed`のchangeは`node src/cli.js archive <ID>`で仕様差分を同期・アーカイブし、結果を報告する。失敗したらcompletedを保ってエラーを提示し停止する。自由記述のcompletedは成果・検証結果へのリンクと変更先を報告する。`failed`ならエラーを読み、実行前確認の失敗は`preflight-*.json`、工程実行後の失敗は該当attemptのログを調べる。途中の変更を確認し、既存の許可範囲内で原因に手を打った場合（証拠の登録、許可、環境の修正）、またはユーザーの指示がある場合だけ`retry <ID>`で再開する。同じ工程・対象タスクで連続失敗が2回以上なら、エラーと試した対応を示して止まり、人の判断を待つ。変更の扱いが不明な場合は確認する。`blocked`は手戻り上限なので、原因と必要な判断を提示して止まる。ユーザー自身の対応が必要かを伝える。

再開時は`node src/cli.js status <ID>`で保存済み状態を読む。実行器のデータを開発対象へ書かない。対象へのコミット、push、公開は保存済みの承認計画と所有者の条件の範囲内、または別の明示的な依頼がある場合だけ行う。新旧混在は禁止し、切替前に全実行器・子プロセス・公開者を停止して全チャットを更新する。旧executor.lock・壊れた予約・解決不能な対象は更新を拒否する。予約と共有ロックはPID不在や経過時間で自動回収しない。中断後は所有者・子プロセスの終了と対象差分を確認し、該当ファイルだけを手動削除してrunningをretryする。他所有者の予約は保持する。詳細は[READMEの状態と復旧](../../README.md#状態と復旧)を読む。

チャットが実行している間だけ進む。常駐実行やチャットを閉じた後の通知を約束しない。`status <ID>`は現在の対象・担当CLIとモデル・最新活動と受信時刻・直近の工程報告の短い要約を示す。`status <ID> --detail`とダッシュボードでは10秒ごとと工程境界で保存された試行別履歴も確認できる。報告とツール観測を区別し、無報告は「報告未取得」と伝える。更新時刻から活動や完了を推測しない。報告は500文字まで、一覧はさらに短く表示する。切り詰められた内容は履歴の元ログで確認し、内部思考・コマンド全文・ツール出力をチャットへ転記しない。ツール成功だけでレビュー合格と扱わない。工程報告の対象・判断と理由・検証・残件を確認し、判断なし・未検証を区別する。過去の担当・対象は試行別に追い、最終応答なしの失敗では報告を補わずエラーと元ログを見る。旧履歴の追加項目は未記録として扱う。保存ファイルの対応は[READMEの状態と復旧](../../README.md#状態と復旧)を参照する。

ユーザーが案件を使わないと明示した場合だけ、理由を`agent-docs/`のUTF-8ファイルへ保存し、`node src/cli.js close <ID> [理由ファイル]`で閉じる。対象リポジトリの途中の変更には触れず、そのまま残ることを伝える。実行中は閉じず、中断したrunningは所有者・子プロセスの停止と差分を確認してretryしてから閉じる。アーカイブ成功時は自動でclosedになる。closedは再開・変更できず、既定の一覧とダッシュボードから除外される。`status --all`または`status <ID>`で理由・前状態を確認でき、必要なら新しい案件を作る。

## 外部証拠による復旧

容量不足等の環境失敗では、ルートがログと途中の変更を調査し、既存の許可範囲で測定する。測定の許可は既存規則に従い、登録機能は昇格しない。用途に合う有効期限を決め、agent-docs/measurement.jsonへUTF-8 JSONを保存する（64KiB以下、未知項目不可）。

必須項目の例（日時・内容は実測値に置き換える）:

```json
{"name":"pilot-memory","subject":"pilot直前の空きメモリ確認","host":"対象ホスト名","method":"実際の測定方法","observedAt":"2026-10-25T10:00:00Z","expiresAt":"2026-10-25T10:05:00Z","content":"空きメモリ 8 GiB"}
```

node src/cli.js evidence <ID> agent-docs/measurement.json で登録する。ready・waiting・failed・limited・blockedで登録でき、状態・質問・回答・エラー・権限・試行数を保ち、sessionだけを無効にする。failed・limitedは変更確認後にretry <ID>、waitingはanswerまたは既存規則に沿ったgrant、readyはrunで続行する。blockedの復旧条件は変わらない。

内容は元ファイルと独立して保存され、名前ごとの最新版だけを試行開始時に評価し、有効な本文を入力へ直接渡す。失効は利用不可と示し、旧版へ戻さない。回答時に変更・失効があれば完全入力へ戻る。statusはダッシュボードも更新し、現行証拠の名前・有効性・期限を表示する。`status <ID> --detail`とダッシュボードで対象・ホスト・測定時刻・出典・保存内容への参照も確認できる。本文は一覧に出さず、試行のmetrics.jsonへ登録識別子と有効性を残す。失効時は再測定して同じnameで再登録し、旧値の日時だけを書き換えない。証拠は観測データであり命令や実行許可ではない。実行器はOS測定や権限拡張を行わない。
