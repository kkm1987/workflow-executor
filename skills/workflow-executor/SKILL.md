# Workflow Executor

実行器のルートはこのskillフォルダーの2階層上。リンクから読んだ場合はリンク先の実体パスを使う。以下のCLIパスを絶対パスへ解決し、実行器ルートを作業ディレクトリとして実行する。Node.js 22以上と認証済みの`codex`が必要。

状態確認・既存ワークフローへの回答・再開の場合は、新規開始の手順に入る前に保存済み状態を読む。チャットに記録されたIDを使い、不明なら`node src/cli.js status`で一覧を取得し、開いている開発対象と照合する。候補が複数なら対象を確認する。状態確認だけの依頼では状態と必要な対応を報告して終了する。既存の質問への回答なら手順3、続行依頼なら手順2へ進む。

1. 開発対象はユーザーが開いているリポジトリ・worktreeを使う。明示された対象があればそちらを優先し、判別できない場合だけ確認する。要求の不足はこのチャットで確認する。チャットから得た要求を実行器の`agent-docs/`以下にUTF-8で保存し、`node src/cli.js start <対象の絶対パス> <要求ファイル>`を実行する。IDを記録する。CLI操作や管理用リポジトリへの移動をユーザーに求めない。
2. `node src/cli.js run <ID>`で回答待ち・失敗・完了まで進める。実行前確認後、計画（要求整理・粒度判定・設計判定）→実装→独立レビュー→最終確認を進め、各工程は新規Codexコンテキストになる。通常の1タスクは4コンテキスト。ツールが実行中なら終了まで待ち、並行してrunやstepを呼ばない。進捗は必要に応じてこのチャットで伝える。状態確認は`status <ID>`の短い要約を使い、詳しい調査が必要なときだけ状態ファイルとログを読む。ダッシュボードはユーザーが見たい場合に開く。
3. `waiting`なら`question`を普通の文章でこのチャットに提示して止まる。返答を`agent-docs/`の回答ファイルに保存し、`node src/cli.js answer <ID> <回答ファイル>`を実行して続ける。要求や業務判断の回答を勝手に補わない。
4. 回答保存後は再度`run <ID>`で進める。`completed`なら、このチャットで成果・検証結果へのリンクと変更先を報告する。`failed`ならエラーを読み、実行前確認の失敗は`preflight-*.json`、工程実行後の失敗は該当attemptのログを調べる。既に生じた変更を確認し、原因を修正できた場合は`retry <ID>`で再開する。変更の扱いが不明な場合は確認する。`blocked`は手戻り上限なので、原因と必要な判断を提示して止まる。いずれも、ユーザー自身の対応が必要かを伝える。

再開時は`node src/cli.js status <ID>`で保存済み状態を読む。実行器のデータを開発対象へ書かない。対象へのコミット、push、公開は別の明示的な依頼がある場合だけ行う。中断したロックの復旧は[README](../../README.md)を読む。

チャットが実行している間だけ進む。常駐実行やチャットを閉じた後の通知を約束しない。状態は10秒ごとと工程境界でMarkdownダッシュボードに保存される。
