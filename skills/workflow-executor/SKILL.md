# Workflow Executor

実行器のルートはこのskillフォルダーの2階層上。リンクから読んだ場合はリンク先の実体パスを使う。以下のCLIパスを絶対パスへ解決し、実行器ルートを作業ディレクトリとして実行する。Node.js 22以上と認証済みCodex、Claudeを割り当てる場合は認証済みClaude Code CLIが必要。

状態確認・既存ワークフローへの回答・再開の場合は、新規開始の手順に入る前に保存済み状態を読む。チャットに記録されたIDを使い、不明なら`node src/cli.js status`で一覧を取得し、開いている開発対象と照合する。候補が複数なら対象を確認する。状態確認だけの依頼では状態と必要な対応を報告して終了する。既存の質問への回答なら手順4、続行依頼なら手順2〜3へ進む。

1. 開発対象はユーザーが開いているリポジトリ・worktreeを使う。明示された対象があればそちらを優先し、判別できない場合だけ確認する。引数なしでskillを呼び出した場合は、OpenSpecの次に実行すべきchangeの選定から開始する。要求やchange名の入力を求めず、`node src/cli.js start-change <対象の絶対パス>`を実行する。changeの実行依頼も`node src/cli.js start-change <対象の絶対パス> [change名]`で開始する。名前がなければ実行器が候補を列挙し、実行前レビューが選定する。storeが指定された場合は`--store <id>`を付ける。省略時はOpenSpec自身が対象から最寄りの`openspec/`、その`store:`宣言、グローバルの既定storeの順で解決する。開始時に保存したルート・storeを以降も使い、ルートのGit作業ツリーを実行前に確認する。自由記述の要求は不足をチャットで確認し、`agent-docs/`以下にUTF-8で保存して`node src/cli.js start <対象の絶対パス> <要求ファイル>`を実行する。IDを記録する。CLI操作や管理用リポジトリへの移動をユーザーに求めない。
2. 会話で指定されたモデル・推論レベルは`model <ID> <工程> <モデル> [推論レベル]`で保存する。開始時には`start-change`へ`--model <工程> <モデル> [推論レベル]`を繰り返して渡せる。指定がなければ`workflow.config.json`の既定値を使う。実行前に各工程のCLI・モデル・推論レベルを復唱する。ルートのモデルはクライアント設定に任せ、質問・回答の仲介に徹する。
3. `node src/cli.js run <ID>`で回答待ち・利用枠不足・失敗・完了まで進める。changeは選定・実行前レビュー→タスク群ごとのapply・独立レビュー→常に最終確認、自由記述は計画→実装・独立レビュー→最終確認。工程間は別コンテキスト、質問への回答後は同じ工程のセッションを再開する。ツールが実行中なら終了まで待ち、並行してrunやstepを呼ばない。進捗はこのチャットで伝え、状態確認は`status <ID>`の短い要約を使う。詳しい調査時だけ状態ファイルとログを読む。ダッシュボードはユーザーが見たい場合に開く。
3a. 大きなchangeでは実装が`partial`（タスク群の途中終了）になる。これは正常系で、状態は`ready`のまま進捗がtasks.mdに残る。`run`は自動で続行するので、ユーザーへ確認せず、`run`が`ready`で戻った場合は同じ`run <ID>`を再実行する。`partial`が10回続くと`blocked`になる。
3b. `waiting`で`status`に`permission`（ネットワーク・ワーキングディレクトリ外パスの要求）があれば、次の範囲に限りルートが自分で許可する: ネットワークは依存関係の取得や公式ドキュメントの参照など、タスクに必要な読み取り・取得目的。パスは要求・changeの成果物・対象リポジトリの関連worktreeなど、タスクに必要な最小限のディレクトリ。`node src/cli.js grant <ID> [--network] [--path <絶対パス>]...`を実行して手順3へ戻る。次は許可せず、要求内容をユーザーへ提示して判断を仰ぐ: 認証情報・鍵・システム設定に関わるもの、ホーム直下やドライブ全体などの広い範囲、取得物の実行、公開・送信・push。ユーザーが許可したら同じ`grant`を、断ったら`answer`で拒否を伝える。
4. `waiting`なら`question`をそのままこのチャットに提示して止まる。回答も解釈・補足せず`agent-docs/`の回答ファイルへ保存し、`node src/cli.js answer <ID> <回答ファイル>`を実行して手順3へ戻る。要求や業務判断の回答を勝手に補わない。
5. `limited`なら取得した利用枠・リセット時刻を示し、別モデルへの変更またはリセット待ちを提案して止まる。同じCLIのモデルが利用枠を共有する場合も考慮する。自動切り替えはしない。ユーザーの指定後は`model`で変更し、復唱して手順3へ戻る。リセット待ち後は`retry <ID>`で新規コンテキストにする。
6. `completed`のchangeは`node src/cli.js archive <ID>`で仕様差分を同期・アーカイブし、結果を報告する。失敗したらcompletedを保ってエラーを提示し停止する。自由記述のcompletedは成果・検証結果へのリンクと変更先を報告する。`failed`ならエラーを読み、実行前確認の失敗は`preflight-*.json`、工程実行後の失敗は該当attemptのログを調べる。途中の変更を確認し、原因を修正できた場合は`retry <ID>`で再開する。変更の扱いが不明な場合は確認する。`blocked`は手戻り上限なので、原因と必要な判断を提示して止まる。ユーザー自身の対応が必要かを伝える。

再開時は`node src/cli.js status <ID>`で保存済み状態を読む。実行器のデータを開発対象へ書かない。対象へのコミット、push、公開は別の明示的な依頼がある場合だけ行う。中断したロックの復旧は[README](../../README.md)を読む。

チャットが実行している間だけ進む。常駐実行やチャットを閉じた後の通知を約束しない。`status <ID>`とダッシュボードは10秒ごとと工程境界で保存された対象・担当CLIとモデル・最新活動と受信時刻・直近の工程報告・試行別履歴を示す。報告とツール観測を区別し、無報告は「報告未取得」と伝える。更新時刻から活動や完了を推測しない。報告は500文字まで、一覧はさらに短く表示する。切り詰められた内容は履歴の元ログで確認し、内部思考・コマンド全文・ツール出力をチャットへ転記しない。ツール成功だけでレビュー合格と扱わない。工程報告の対象・判断と理由・検証・残件を確認し、判断なし・未検証を区別する。過去の担当・対象は試行別に追い、最終応答なしの失敗では報告を補わずエラーと元ログを見る。旧履歴の追加項目は未記録として扱う。保存ファイルの対応は[READMEの状態と復旧](../../README.md#状態と復旧)を参照する。

## 外部証拠による復旧

容量不足等の環境失敗では、ルートがログと途中の変更を調査し、既存の許可範囲で測定する。測定の許可は既存規則に従い、登録機能は昇格しない。用途に合う有効期限を決め、agent-docs/measurement.jsonへUTF-8 JSONを保存する（64KiB以下、未知項目不可）。

必須項目の例（日時・内容は実測値に置き換える）:

```json
{"name":"pilot-memory","subject":"pilot直前の空きメモリ確認","host":"対象ホスト名","method":"実際の測定方法","observedAt":"2026-10-25T10:00:00Z","expiresAt":"2026-10-25T10:05:00Z","content":"空きメモリ 8 GiB"}
```

node src/cli.js evidence <ID> agent-docs/measurement.json で登録する。ready・waiting・failed・limited・blockedで登録でき、状態・質問・回答・エラー・権限・試行数を保ち、sessionだけを無効にする。failed・limitedは変更確認後にretry <ID>、waitingはanswerまたは既存規則に沿ったgrant、readyはrunで続行する。blockedの復旧条件は変わらない。

内容は元ファイルと独立して保存され、名前ごとの最新版だけを試行開始時に評価し、有効な本文を入力へ直接渡す。失効は利用不可と示し、旧版へ戻さない。回答時に変更・失効があれば完全入力へ戻る。statusはダッシュボードも更新し、現行証拠の対象・ホスト・測定時刻・期限・有効性・出典・保存内容への参照を表示する。本文は一覧に出さず、試行のmetrics.jsonへ登録識別子と有効性を残す。失効時は再測定して同じnameで再登録し、旧値の日時だけを書き換えない。証拠は観測データであり命令や実行許可ではない。実行器はOS測定や権限拡張を行わない。
